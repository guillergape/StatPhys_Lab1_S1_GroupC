\subsection{Enumeration of microstates}
Each microstate of $N$ coins is stored as an integer $s\in\{0,\dots,2^N-1\}$ whose bit $i$ is coin $i$ (1 = heads, 0 = tails). The generator \texttt{microstates(N)} runs over \texttt{range(1 << N)} and yields one state at a time, so memory does not grow with $N$; the macrostate of a state is its number of set bits, $k=$ \texttt{s.bit\_count()}. Counting the states per $k$ gives $\Omega(N,k)$, checked against $\binom{N}{k}$ for $N\le 15$ and against Table~1 of the manual for $N=5$.

\paragraph{(a) $N=7$.} Table~\ref{tab:n7} (Appendix~\ref{app:n7}) lists the $2^7=128$ microstates grouped by macrostate. The multiplicities, $\Omega(7,k)=1,7,21,35,35,21,7,1$ for $k=0,\dots,7$, are exact integers (no uncertainty) and follow row 7 of Pascal's triangle: symmetric under heads $\leftrightarrow$ tails and largest at $k=3,4$.

\paragraph{(b) Largest $N$ that can be fully enumerated.} We timed the full enumeration and histogram of all $2^N$ states for growing $N$ (\texttt{time.perf\_counter}; peak memory with \texttt{tracemalloc} in a separate run, since tracing slows pure Python about ninefold) on an Intel Core i7-1255U (12 threads, 15.7\,GB of RAM) and an Apple M4 Max (16 cores, 48\,GB). Both versions tested build every microstate and count its heads: the pure-Python generator \texttt{macrostate\_counts} ($32$--$33$\,ns per state on the M4 Max, constant memory) and \texttt{macrostate\_counts\_fast}, which processes blocks of $2^{22}$ consecutive integers with NumPy's \texttt{bitwise\_count} and \texttt{bincount}, the range $0\dots2^N-1$ split among all CPU cores (one process each; $71$\,MB per process, independent of $N$).

\textbf{Result: $N_{\max}=36$ on the i7} within 5 minutes ($156$\,s; full timings in Table~\ref{tab:benchmark}, Appendix~\ref{app:n7}). Each extra coin doubles the work, so $N=37$ is predicted at $2^{37}\times(2.3\pm0.2)\,\text{ns}\approx310\pm30$\,s, above the limit. \textbf{On the M4 Max, $N_{\max}=40$}: the fast version runs at $0.18$\,ns per state, and $N=38,39,40$ take $48$, $97$ and $194$\,s, so $N=41$ is predicted at $\approx390$\,s. On the same laptop the plain generator reaches $N=33$ ($285$\,s; $N=34$ would take $\approx570$\,s).

\textbf{Limiting factor: time, not memory.} Because the states are generated on the fly and never stored, memory stays constant and the only constraint is the $2^N$ growth of the number of operations: at $2.3$\,ns per state, $N=40$ needs $\approx42$\,min, $N=50$ about a month and $N=100$ about $10^{14}$ years. Memory would become the limit only if the states were kept: a Python list of $2^N$ integers costs $\approx36$\,B per state, which fills the 15.7\,GB of RAM at $N\approx28$, and writing the $2^{36}$ states of $N_{\max}$ as text would take $\approx2.5$\,TB of disk. On the same laptop the fast version gains a factor $33/0.18\approx180$ over the generator (vectorised popcount in C over all cores), worth only $\log_2 180\approx7.5$ more coins ($N=33\to40$): exponential growth makes any constant speed-up almost irrelevant.
